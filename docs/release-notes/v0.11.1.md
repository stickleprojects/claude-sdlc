## CI and the title check cancel a PR's stale runs

`ci.yml` and `pr-title.yml` had no `concurrency` block. When a PR got a new push, the run for its old head kept going (#138). On a self-hosted runner that runs one job at a time, that's real time. In spellbound3d, `/build` opened a PR and pushed its bookkeeping commit straight after. The runner spent 6–8 minutes on `make check` for the old head while the current head's CI queued behind it, and someone had to cancel the stale run by hand. The agent App can't do that itself: it has no `actions: write` permission.

- **CI:** a new push to a PR cancels that PR's older run, whether it's queued or in progress. The required `check` then reports on the PR's current head, as before. Pushes to `main` are never cancelled or replaced. Each gets a group of its own commit, so every merge gets its own full result. A shared group would not do: it keeps only one pending run, and the next merge would replace it.
- **PR title:** a newer push or title edit on the same PR cancels the older check.

The Claude review already cancelled its stale runs this way.

## Upgrade steps

These are for Claude, as part of `/sdlc`. Do them with the person, after the sync and before `make check`.

1. **Come from v0.11.0.** A repo on v0.10.x or earlier does v0.11.0's upgrade steps first (`docs/release-notes/v0.11.0.md`).
2. **Local edits to `ci.yml` or `pr-title.yml`.** If the sync lists either as a conflict, keep the new top-level `concurrency:` block whole, along with the project's own steps. A project with its own `concurrency:` block in either file keeps one block, and pushes to `main` must still each get a group of their own (`github.sha`).
3. Nothing else: no settings, and branch protection doesn't change.
