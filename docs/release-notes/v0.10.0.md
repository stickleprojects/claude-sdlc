## Breaking: every repo requires the Claude review of the latest commit

Main now requires the **`claude-review`** commit status in every repo, solo or team, with auto-merge or without, so nobody merges on a stale review (#46).

**How the status is set:**
- **The review job posts it itself:** *pending* when it starts; *success* once the review summary is posted, or, for a PR that changes a `claude-*.yml` workflow, with a description saying a code owner reviews it by hand; *failure* if the review fails, or if the review action finishes without posting or editing its summary during the job (`scripts/review-posted.sh`): an action that ends early, with tool calls refused, no longer counts as a review. A job skipped by its `if` (an unrelated label, say) posts nothing, so it can't satisfy the gate the way the job's old `review` check run could (#101).
- **A push the review doesn't cover** (auto-merge off) gets a *failure* from the new `unreviewed-push` job: "Not reviewed: 2 commits since the review of abc1234. Add the review label". Every commit after a review needs a new one, docs and sketches too. The skills add the label after they push a fix (`scripts/request-review.sh`); a person adds it on GitHub.

**What else changes:**
- **Bootstrap** requires `claude-review` alongside `check` and `pr-title`, in every mode, and drops the old `review` check.
- **`scripts/auto-merge.sh`** counts only `claude-review` as the gate. On a branch that still requires `review`, it skips with a warning to re-run bootstrap. It also never auto-merges a PR that changes a `claude-*.yml` workflow, because the AI review can't run on one.
- **Until bootstrap is re-run,** nothing breaks: main keeps its old required checks, but the pipeline doesn't turn auto-merge on.

## Breaking: a PR's title says which gate artifact it changes

The *PR title* check fails a PR that changes `changes/<slug>/intent.md`, `bug.md`, `spec.md` or `plan.md` unless its type is `intent`, `bug`, `spec` or `plan` (any of the ones it changes), so the merge record shows a gate artifact was accepted (#46). A spec amended under `docs:` or `feat:` now fails. Code PRs, which change only `build.md` and code, are unaffected.

## Optional: run the pipeline on your own runner

Every framework job now runs on the runner named by the repository variable **`SDLC_RUNNER`**, or on `ubuntu-latest` when it isn't set, so nothing changes unless you set it (#126). Set it with `gh variable set SDLC_RUNNER --body self-hosted`. Use it for a while when GitHub-hosted runners are down, or for good to stop paying for Actions minutes. `gh variable delete SDLC_RUNNER` moves the checks back. Code from outside the repo always stays on GitHub-hosted runners: PRs from forks (including deleted ones) and comment-triggered runs on any PR. If the repo limits which actions may run, allow `oven-sh/setup-bun`: `claude-code-action` uses it internally. On a public repo, the sync warns if `SDLC_RUNNER` is set while some fork PRs can run workflows without a maintainer's approval, because a fork PR can edit its workflow to reach your runner. `docs/self-hosted-runner.md` covers what the runner needs and how to lock it down.

## Fixes from the v0.6.0 → v0.8.0 sync review (#101)

- **`SDLC_AUTO_MERGE=off` is off everywhere.** Case doesn't matter, and unset, empty or `off` means off. The rule is written once (`scripts/auto-merge.sh --method`), and the workflow, bootstrap, the sync and `scripts/request-review.sh` all follow it, so a repo set to `off` no longer runs a review on every push.
- **No stale confirmation when auto-merge is off.** Bootstrap deletes a leftover `SDLC_AUTO_MERGE_CONFIRMED`.
- **Rulesets-only branches decide for themselves.** A leftover confirmation no longer stands in for a ruleset that doesn't dismiss stale approvals. Organization variables past the first 30 are read too.
- **Merged specs' criteria are left alone.** `make validate` checks the `- AC<n>` form only in specs the branch adds or edits.
- **The sync reports the repo's own scripts that aren't executable,** with the fix command, and leaves them unchanged.
- **The "AI review can't run" note** is also posted on the push that first changes a `claude-*.yml` workflow.

## Optional: project rules for the review, without editing REVIEW.md

`REVIEW.md` has a new last pass, **Project rules**. If the repo has `docs/review-rules.md`, the review applies each rule in it to the diff, at the severity the file gives. The file is the project's own: the sync never touches it. Until now, the only way to add project rules was to edit `REVIEW.md`, which clashed with every framework update. `templates/review-rules.md` is a starting point.

## Optional: a roadmap of milestones that `make validate` checks

A project can now keep an ordered roadmap in `docs/roadmap.md` (#81). It's a list of milestones, each with a goal, a scope, exit criteria as checkboxes and a status, and a `### Changes` table with one row per change. The format comes from spellbound3d and is described in `docs/roadmap-format.md`; `templates/roadmap.md` is a starting point. The file is the project's own, and the sync never touches it.

- **Nothing changes without one.** The check runs only when `docs/roadmap.md` exists.
- **With one, `make validate` fails** when they disagree: every intent needs a `Milestone: M<n>` line and one row under that milestone, each row's status must match the change's state as `make next` reads it (a merged build is `✅ done`), and a done milestone has only done or withdrawn rows and every exit criterion ticked. Bug changes are never on the roadmap.
- **Scope changes get adjustment records** in `docs/roadmap/adjustments/` (`templates/roadmap-adjustment.md`), written in the intent PR and never edited away. An intent cites one with an `Adjustment:` line.
- **`/intent` places each new change** on the roadmap, in the same PR: the `Milestone:` line, the `planned` row, any adjustment, and a *Roadmap* section in the PR body. **`/build`** marks the row `✅ done` in the build PR, and asks the person before marking a milestone done.
- **`/next` shows the current milestone:** its changes that aren't done and its open exit criteria, and offers `/intent` for the next piece of it.
- **Upgrading a repo that already has a roadmap:** see upgrade step 5. spellbound3d's roadmap passes unchanged. jobhunt-app's list of items converts to milestones.

## Upgrade steps

These are for Claude, as part of `/sdlc`. Do them with the person, after the sync and before `make check`.

1. **Switch main to the new gate (every repo).** The person runs this themselves, because it needs admin access to the repo:

   ```
   scripts/bootstrap-github.sh --mode <solo|team>   # the mode the repo already uses
   ```

   Check its step 6 line: it should list the `'check', 'pr-title' and 'claude-review'` statuses, and say "the old review check is no longer required" if `review` was required before. With auto-merge off, it also deletes a leftover `SDLC_AUTO_MERGE_CONFIRMED`. Until this is done, main keeps its old checks and `scripts/auto-merge.sh` doesn't enable auto-merge.
2. **Open PRs need a review of their latest commit.** Once bootstrap has run, a PR whose latest commit has no `claude-review` status waits on it. List the open PRs, and for each one ask the person whether to request a review now (`scripts/request-review.sh <N>`, which adds the `review` label) or leave it until its next push.
3. **Open PRs that change a gate artifact under the wrong type.** For each open PR that changes `changes/*/intent.md`, `bug.md`, `spec.md` or `plan.md`, check its title's type. Offer to retitle the ones that don't match, for example `docs(0007): …` to `spec(0007): …`. Retitling is the PR author's call, so ask first.
4. **Move local `REVIEW.md` rules into `docs/review-rules.md`.** Check whether the sync listed `REVIEW.md` as a conflict, or under "kept your local changes". If it did, the repo has added its own rules there. Show the person the local additions (`git diff <the previous sync's commit> -- REVIEW.md`, or the conflict's *yours* side). Offer to move them, as rules, into `docs/review-rules.md`, starting from `templates/review-rules.md`. Then take the framework's `REVIEW.md` unchanged, so later syncs merge it cleanly. Do this in the sync PR, because it resolves the sync's own conflict. If the person prefers to keep their edit, resolve the conflict by hand as usual.
5. **The roadmap.** The check starts as soon as the repo has `docs/roadmap.md`, so it applies on this sync PR's own `make check`. Find which case the repo is in:
   - **It has its own roadmap check already** (spellbound3d: `tools/standards/roadmap_check.py`, and local edits to `templates/intent.md` and `.claude/skills/intent/SKILL.md` that the sync lists as kept or as conflicts). The framework now does the same check. In the sync PR, with the person: take the framework's `templates/intent.md` and intent skill unchanged; remove the local checker's line from `make validate` in the Makefile, and the checker itself unless it holds project-only rules; keep `docs/roadmap.md` and `docs/roadmap/adjustments/` as they are (the framework reads that format, and the adjustments README can stay or go). Offer to mark the ADR that introduced the local check (spellbound3d's ADR 0009) as superseded, or to add a note to it. Then run `make validate`: it should pass with no roadmap edits.
   - **It has a `docs/roadmap.md` in another shape** (jobhunt-app: an ordered list of items, with *Done* and *In progress* tables and no `## M<n>:` milestones). `make validate` fails until it's converted. Propose the conversion to the person, because the roadmap's order and grouping are the product owner's:
     - each numbered item becomes a milestone at `draft`, in the same order, with its reason as the **Goal** and the sources it cites in **Scope**;
     - the changes in *Done* that came before the roadmap go into an `M0: Before the roadmap · ✅ done` milestone, with one ticked exit criterion saying what they delivered;
     - an item that has a change in progress gets its changes as rows. It stays `draft`, which needs no exit criteria yet; the product owner writes them and moves it to `agreed` or `in progress` later;
     - work the list put between items, such as jobhunt-app's security checks before phone access, becomes a row in the milestone it comes before, with an adjustment record saying why;
     - *Later* stays as it is (it isn't checked);
     - every intent gets its `Milestone:` line, and a rule in `CLAUDE.md` asking intents to name an item is removed (the intent skill now does it).

     Do the conversion in the sync PR, so `make check` passes on it, and say in the PR body that the product owner should look over the roadmap. If they'd rather convert it later, rename the file in the sync PR (`git mv docs/roadmap.md docs/roadmap-draft.md`) and convert it in its own PR.
   - **Open PRs** that add an intent, in a repo with a roadmap, fail `make check` once they merge main, until they add their row and `Milestone:` line. List them for the person.
   - **No roadmap.** Nothing to do. Mention in one line that the repo can start one from `templates/roadmap.md` (`docs/roadmap-format.md`).
6. **Repo-owned scripts.** If the sync listed "your own scripts that aren't executable in git", offer to run the `git update-index --chmod=+x` command it gives, and commit the result in the sync PR.
7. **Report** in the sync PR body:
   - whether bootstrap was re-run, or is still waiting for the person;
   - which open PRs had a review requested, or were retitled;
   - any scripts that were made executable;
   - whether local `REVIEW.md` rules moved to `docs/review-rules.md`.
   - the roadmap: whether a local check was replaced by the framework's, or the roadmap was converted (and that the product owner should review it), or renamed for later.
