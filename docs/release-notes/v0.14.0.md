## Fix: Update branch keeps the review only when it's safe to

In v0.13.0, a push that only merged `main` in (GitHub's **Update branch**) was meant to keep the PR's review (#182). It compared diffs, and diffs include their surrounding lines, so it failed whenever `main` had edited a line next to the PR's own: in practice, nearly always. Now a review carries forward only when all of these hold (#182, #194):
- each commit since the review is a merge of the reviewed head with a commit on the base branch;
- git's own merge of those two gives exactly that commit, so the merge added nothing;
- `main`'s changes that it brings in touch none of the files the PR changes.

Otherwise `claude-review` says "Not reviewed", naming the shared file if that's the reason, and the `review` label runs a fresh one. Two edits to one file can reword the same rule and still merge cleanly, and only a review sees the clash. The check needs git 2.38 or newer on the runner; with older git, every push needs a review, as before.

## New: a new intent names its milestone

With a roadmap (`docs/roadmap.md`), `make new-change` writes a live `Milestone: M<n>` line under `Product owner:`. `make validate` fails it until the milestone is filled in (#187).

## New: the check job keeps your test reports

Have `make check` write test reports under `reports/`, and `sdlc-ci.yml`'s `check` job keeps them as the `reports` artifact, pass or fail (#188). With `SDLC_CHECK_AFTER_REVIEW` on, a PR's `check` runs with main's privileges and uploads nothing, because an action that runs after PR code there could be tampered with. Pushes to main still upload.

## New: how a consumer asks for a change to the framework

`.sdlc/docs/consumer-requests.md` is the protocol a consumer's AI and the framework's AI follow to agree a change to the framework's rules, or that a consumer's AI follows on its own to file one issue (#186).

## Smaller changes

- The descopes check no longer runs for the reviewer's own reviews (#189).
- `.sdlc/docs/self-hosted-runner.md` explains why a runner that keeps its workspace between jobs should drop `refs/remotes/pull/*` when it scans every ref for secrets (#189).

## Optional: review every push, base merges included

The repo variable `SDLC_REVIEW_CARRY_FORWARD` defaults to on. Set it to `off` (`gh variable set SDLC_REVIEW_CARRY_FORWARD --body off`) and every push needs a fresh review, Update branch included, as before #182.

## Upgrade steps

These are for Claude, as part of `/sdlc`. Do them with the person, after the sync and before `make check`.

1. **A Milestone override.** If `.sdlc-local/templates/intent.md` exists only to make the `Milestone:` line live, delete it in the sync PR. Otherwise new intents get two `Milestone:` lines, which `make validate` fails. If it overrides other things, remove just the `Milestone:` part.
2. **A report upload.** If the project added its own step to `sdlc-ci.yml` to upload test reports, move the reports under `reports/` and drop the step. The sync's merge may otherwise keep both.
3. **git on a self-hosted runner.** If `SDLC_RUNNER` is set, ask the person to check that the runner's git is 2.38 or newer (`git --version`). Older git is safe, but Update branch then always needs a review.
