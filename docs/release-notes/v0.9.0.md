## Breaking: new and edited specs need requirements the checks can read

Every line under a spec's `## Requirements` must be a requirement in the form `- R<n>. <requirement>` (a letter suffix such as `R14a` is fine, and so are `**R1**` and `1. R1`). Group labels such as `**Tests**`, indented lines that continue a requirement, and prose paragraphs are left alone. The templates now show an example requirement line.

**What `make validate` checks.** It checks only a `spec.md` that your branch adds or edits compared with main. Specs merged before this release stay valid until someone edits them. In an added or edited spec, it fails when:

- a top-level list entry under `## Requirements` isn't `R<n>` (for example `- Requirement 7: …`, or a bare `- …`);
- an `R<n>` line has no text;
- no requirement can be read at all.

**Why.** The new clause coverage check (below) works one requirement at a time, and a requirement it can't read would go unchecked without anyone knowing (PR #107 review).

## Clause coverage: every part of a requirement is tested and planned

Until now every check compared IDs: each requirement has an acceptance criterion, each criterion has a Verification row. A criterion that tested only part of its requirement passed (issue #47).

- **Spec PRs:** the review splits each requirement the PR adds or changes into clauses, one per separate outcome. Every clause needs a criterion that tests it, or an entry `- Untestable (R<n>): "<clause>" because <reason>.` under Acceptance criteria. An uncovered clause is an Important finding for the product owner. `/spec` applies the same split when it drafts.
- **Plan PRs:** each requirement the PR touches is compared with the plan's design and Verification rows, from the requirement's text, not only its criteria. A missing clause is Important, for the engineer.
- **Done work is left alone.** The review checks only the requirements a PR adds or changes, and those whose criteria or plan rows it changes. Untouched requirements in merged specs aren't re-reviewed.
- **The verifier** reports PASS or FAIL per clause. Its last line now counts failing clauses: `VERDICT: FAIL (<n> criteria failing, <c> clauses failing, <m> unapproved descopes)`.
- **`make clauses CHANGE=0002`** prints the spec as one JSON block per requirement, holding its text, the criteria that cite it, and the plan and build.md lines that cite it.

## The verifier compares what was built with each requirement

Passing criteria don't prove a requirement was built: a criterion can test the data beneath a feature that never shipped (issue #106, from spellbound3d 0009).

- **The verifier** compares what the code and build.md's milestone Goals and Demos deliver with each requirement's wording, one requirement per call (`scripts/clause-check.sh --stage build`). A gap where the delivery lacks the requirement's main verb or noun ("generates a scene", and the code only draws a diagram) is **large**. A gap in a modifier only is **wording drift**, and is just noted.
- **No routine sign-off.** A person is asked only about a large gap that nothing has approved: no `Approved:` descope in the plan, no answered build.md deviation, nothing under the spec's Out of scope. An approval counts only if its quote is really in the change's files.
- **How it reaches the product owner:** `/build` puts each such gap first in the PR body under **Descope: needs approval**, and the review raises it as an Important thread. The product owner approves it as a descope or sends it back to be built. In team mode, the open thread holds the merge until then.
- **`/build`** also checks each milestone's Goal and Demo against its requirements when it writes build.md, and raises a narrowed requirement before approval rather than at the end.
- **Cost:** each verifier run makes one sonnet call per requirement, through your local Claude subscription at build time. Nothing new runs in CI for code PRs.

## Optional: the `clauses` make target

The Claude review runs a cheap clause check on spec and plan PRs (one haiku call per changed requirement) when your Makefile has a `clauses` target. Without it, nothing fails: the review skips that step quietly and splits the clauses itself. Upgrade step 1 below adds it.

## Upgrade steps

These are for Claude, as part of `/sdlc`. Do them with the person, after the sync and before `make check`.

1. **Add the `clauses` target (in the sync PR).** The sync lists it under the optional targets the Makefile lacks. Add it next to the `next` target, calling the pipeline CLI the same way `next` does (usually `$(SDLC)`), and add `clauses` to `.PHONY`:

   ```
   # One block per requirement, for scripts/clause-check.sh. CHANGE=0002 is required.
   clauses:
   	@test -n "$(CHANGE)" || { echo "usage: make clauses CHANGE=0002 [REF=origin/main]"; exit 2; }
   	@$(SDLC) clauses $(CHANGE) $(if $(REF),--ref $(REF))
   ```

   Check it with `make clauses CHANGE=<a change that has a spec>`. It prints JSON.

2. **Find the in-flight work.** Run `make next REF=origin/main` and list the open PRs. A change is **in flight** when its code hasn't merged: its next step is spec, plan or build, or it has an open intent, spec, plan or code PR. A change whose code has merged is **done**: leave it alone. Show the person the list before going on.

3. **Make each in-flight spec readable.** For each in-flight change with a spec, run `make clauses CHANGE=<slug>`. Each `warning: can't read this as a requirement` names a line to rewrite as `- R<n>. <the same words>`, keeping the requirement's wording and number exactly. This is a format fix, which Claude owns, so it needs no product decision. Make it where the spec lives:
   - **The spec is in an open PR:** push the fix to that PR's branch, with the message `spec(<slug>): requirements as R<n> bullets`.
   - **The spec has merged, and the change is still in flight:** leave it, because `make validate` doesn't check it until someone edits it. Fix the format as part of the next edit.

   Run `make validate` on each branch you push to.

4. **Check clause coverage on in-flight specs and plans.** For each in-flight change, run `scripts/clause-check.sh --stage spec <slug>`. If its plan isn't built yet, also run `--stage plan`. Confirm each entry by reading the spec and plan. Then list what's uncovered, quoting each clause:
   - **A clause no criterion tests** is the product owner's decision: a new criterion changes the spec. For a spec PR that's still open, raise it in that PR's review (`/pr <N>`). For a merged spec, offer a spec amendment PR. Never add criteria yourself.
   - **A clause the plan doesn't design or verify** is the engineer's: offer a plan amendment (`/plan`).

5. **Check what's being built.** For each change that's mid-build (an approved build.md in progress, or a code PR open), run `scripts/clause-check.sh --stage build <slug>`. Raise each large gap with no approval with the engineer: build it in a coming milestone, or record a descope for the product owner to approve. Small gaps (wording drift) need no action. Doing this now finds gaps before the verifier does at the end of the build.

6. **Report** in the sync PR body, under **In-flight work**:
   - the target you added;
   - each spec PR you pushed a format fix to;
   - each gap found, with who decides it.

   Steps 4 and 5 call the model once per requirement, so tell the person roughly how many requirements that is before running them on a large backlog.
