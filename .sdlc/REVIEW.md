# .sdlc/REVIEW.md

The policy for automated PR review (`.github/workflows/sdlc-claude-review.yml`). Review findings are comments and threads. The review never approves a PR; its open Important threads hold the merge until they're resolved, and a human merges it (in team mode, after a code owner's approval). The agent that wrote a change never reviews, approves or merges it. <!-- rule: review.never-approves -->

## Passes

Run these in order. Report only what each pass actually finds.

1. **Bugs:** logic errors, unhandled failure paths, broken edge cases, races. Code that parses text people write, such as artifact sections, must fail safe: input it doesn't recognise must not quietly read as "empty", "none" or "done". <!-- rule: review.bugs -->
2. **Security:** follow `.sdlc/skills/security-policy/SKILL.md`. Watch for secrets in diffs, unvalidated input, and new dependencies without a stated reason. <!-- rule: review.security -->
3. **Compliance with the artifact chain:** the PR's change folder under `changes/` must have `intent.md`, `spec.md` and `plan.md`. A bug has `bug.md` in place of `intent.md`, and a short spec (requirements, and one acceptance test per symptom), which is complete as it is. A `build.md`, if present, is the approved build plan: its deviations and anything marked `Engineer decides: yes` should appear in the PR body. Flag code that has no matching requirement, requirements with no code or test, and plan steps that were skipped. <!-- rule: review.chain -->
   - **The bug fast path** (#148): a `fix(<slug>): …` PR that carries the change's `bug.md` and short `spec.md` with the failing tests and the fix needs no `plan.md`. Check it at both levels: the bug and spec for completeness, as for a bug PR, and the code against the spec's acceptance criteria. Each criterion has a test, and the failing tests come first, in a `test(<slug>): …` commit before the fix. If the bug is too big for one PR (it needs a design decision, a new dependency or a plan to build), report that as Important: it takes the full path, with a plan. So is a fast-path PR in a repo whose `CLAUDE.md` has the line `Bug path: full` (the `pr-title` check fails it too). Until #151, GitHub doesn't require the product owner's approval on such a PR, so say in the summary that the bug and spec need it. <!-- rule: review.bug-fast-path -->
   - **The tooling path** (#221): a `chore(<slug>): …` or `ci(<slug>): …` PR whose `intent.md` has the line `Kind: tooling` carries the intent, `plan.md` and the code, with no spec. The plan's Verification rows stand in for acceptance criteria: each has its test or command, and no plan step is skipped. If the change alters how the product behaves (not only scripts, CI support or dev tools), report that as Important: it takes the full path, with a spec. The *engineer* decides. <!-- rule: review.tooling-path -->
   - **Maintenance exemption:** skip this pass for PRs whose title starts with `fix:`, `ci:` or `chore:` with no scope (a `fix(<slug>)` names a change and is never exempt), but only if they don't change how the product behaves. That covers pipeline, tooling, docs and file permissions. For these, check instead that the PR description explains why the change is needed. If an exempt PR does change product behaviour (`src/` logic, CLI output), report that as Important: it needs an intent. <!-- rule: review.maintenance-exemption -->
   - PRs that only add or edit artifacts (`intent:`, `bug:`, `spec:`, `plan:`) are checked only against the stage they belong to. <!-- rule: review.artifact-stage -->
   - **Plan PRs and architecture decisions:** read the repo's ADRs (`docs/adr/*.md`, if any). If the plan does what an accepted ADR's **Revisit when** line describes, or makes an architecture choice no ADR covers (a new framework, service or datastore, reliance on a library's undocumented internals, or building by hand something a widely used library provides when an earlier change already did), its **Risks** must have an `Architecture decision needed:` line naming the question, the ADR and trigger (or "no ADR"), and the engineer's decision. Report a missing line as Important, quoting the plan text that meets the trigger and the trigger itself; the engineer decides. A plan that builds by hand what a widely used library provides, without saying why in **Approach**, is a Nit. <!-- rule: review.adr-trigger -->
   - **ADR PRs** (`docs/adr/`): an accepted ADR's **Revisit when** lines are concrete enough to check against a single plan ("a plan hand-builds navigation state", not "if it gets complex"). Report vague triggers as Important; the tech lead decides. <!-- rule: review.adr-triggers-concrete -->
   - **Repos that track changes as issues:** if the repo's `CLAUDE.md` contains the line `Change tracking: issues` (the claude-sdlc framework repo does), skip the change-folder requirement for every PR type, `feat:` included. Instead, check that the PR description links an issue, or explains the problem it solves and how the change was tested. Report a missing explanation as Important. <!-- rule: review.issue-tracking -->
   - **Clause coverage (`spec:` PRs, and PRs that change a `spec.md`):** checking that each requirement has a criterion isn't enough, because a criterion can test only part of its requirement (#47). Split each requirement the PR adds or changes into clauses (`.sdlc/skills/scope.md`, *Clauses*). Every clause is tested by at least one acceptance criterion, or listed under Acceptance criteria as `- Untestable (R<n>): "<clause>" because <reason>.` An uncovered clause is Important: quote the clause, name its requirement, and suggest the criterion that would test it. The *product owner* decides, because a new or changed criterion changes the spec. <!-- rule: review.clause-coverage-spec -->
4. **Verification:** every acceptance criterion has a test or a command in the plan's Verification section. Bug fixes include a test that failed before the fix. <!-- rule: review.verification -->
   - **At the right level:** the test drives the criterion at the level it describes (`.sdlc/skills/scope.md`). A UI behaviour tested only through the model beneath the UI, or a criterion whose only evidence is a file that exists, is Important. <!-- rule: review.test-level -->
   - **Clause coverage (`plan:` PRs, and PRs that change a `plan.md`):** for each requirement the PR adds or changes, and each one whose criteria or plan rows it changes, compare the plan with the requirement's text, not only with its acceptance criteria. Leave requirements the PR doesn't touch alone: done work isn't re-reviewed. Every testable clause has a design statement in the plan and a Verification row that would fail if the clause weren't met. A clause missing either is Important, quoted with its requirement; the *engineer* decides. <!-- rule: review.clause-coverage-plan -->
   - **Every clause of a requirement in one finding (#160).** Before you write a clause finding, split the *whole* requirement, start to end, each item of a list included, not just the first gap you see: a gap left for the next review costs the author another push, CI run and review. Post one thread per requirement that lists every clause, each with the criterion (or plan line and Verification row) that covers it, or "none". Suggest wording that covers every uncovered clause at once. <!-- rule: review.clause-one-finding -->
   - **The design text that depends on it, in the same pass (#172).** When a PR changes a requirement and the change has a `plan.md` (on the branch or on `main`), read every plan statement that depends on that requirement (Approach, Steps, Verification rows) against its new text in the same review, not after the clauses are fixed. A statement the change makes false or incomplete ("stays on the medium rig" after the requirement moves to the large one) is Important: quote it with the requirement, in that requirement's clause thread where there is one. The *engineer* decides whether the plan is amended in this PR or in a plan PR. <!-- rule: review.dependent-design -->
   - **On a re-review, the first split stands (#160).** For a requirement that already has a clause thread from an earlier review (resolved or not), compare its text now with its text at that thread's commit: `gh api repos/<repo>/pulls/<N>/comments --jq '.[] | select(.in_reply_to_id == null) | [.original_commit_id, .body[0:80]]'`, then `git diff <sha> HEAD -- <spec.md or plan.md>`. If that commit is no longer in the repo (the branch was force-pushed or rebased), treat the whole text as changed and review it as a first review would. In text that hasn't changed, raise no new clauses: check only that the clauses that thread listed are now covered. A clause you'd have split out of unchanged text is a Nit at most. New clause findings come only from text added or reworded since that commit, or from requirements no earlier thread covered. <!-- rule: review.rereview-first-split -->
   - **Where the clauses come from:** when the review prompt includes the clause check's output (`.sdlc/scripts/clause-check.sh`, one small-model call per requirement), start from it. Confirm each entry against the files before reporting it, and report each `unchecked` entry as a requirement the check couldn't read, never as covered. An entry with no `requirement` that says the check could not run isn't a finding: say so in one line of the summary and split the requirements yourself. Without the file (a repo with no `make clauses` target, or no spec or plan changed), split the requirements yourself, one at a time. <!-- rule: review.clause-check-input -->
5. **Descopes:** silence is not permission, and a rule's scope is a minimum (`.sdlc/skills/scope.md`). Report as Important anything the PR leaves undone, untested or unchecked that nobody has approved: wording such as "not tested", "manual", "skipped", "out of scope", "not covered" or "like the rest of …" in a plan, build.md, PR body or code comment; new `skip` or no-cover markers; and first-party files the PR adds or edits under a lint, format, type-check or coverage exclusion. A descope is approved only as `scope.md` records one: a `Descope: … Approved: <name>, <date>.` entry in the plan's **Descopes** (one still in Risks counts as not approved), a build.md deviation the engineer has answered (the PR body's, for a small build), or the spec's **Out of scope**, which the product owner decides. Quote the text, and say who decides. A plan whose `- **Definition of done:**` line leaves out a kind the change plainly is (a UI change that doesn't name UI), and a code PR that falls short of a row its plan names (`.sdlc/templates/definition-of-done.md`, with the repo's `docs/definition-of-done.md` on top), are Important too, unless an approved descope covers the gap. A code PR whose body doesn't list each of the plan's `Human check:` entries under **To check by hand** is Important too: the owner has to see them before merging. <!-- rule: review.descopes -->
   - **What was delivered, against each requirement (code PRs, #106):** passing criteria don't prove a requirement was built. For each requirement the PR implements, compare its wording with what the diff delivers and with build.md's milestone Goals and Demos. When the gap is large (`scope.md`, *Delivery gaps*) and no `Approved:` descope, answered deviation or Out of scope entry covers it, post an Important finding that starts **Descope: needs approval**, quoting the requirement and what was delivered; the *product owner* decides: approve it as a descope, or send it back to be built. Where branch protection requires resolved conversations, the open thread holds the merge until they do. Post one for each entry the PR body lists under **Descope: needs approval**, too. A gap in a modifier only is wording drift: mention it in the summary, not as a finding. <!-- rule: review.delivery-gap -->
   - **A build PR that amends its plan (#174):** only when the review prompt says the repo variable `SDLC_BUILD_AMENDS_PLAN` is `on`. Then a code PR may change its own change's `plan.md`, and its `spec.md` where a decision changes a clause, if its body lists each amendment under `## Plan changes`. List every amendment the diff makes, with build.md's record of it quoted (who decided, when, and their words), in the one **Session decisions** thread below. A person's one `Approved: <name>, <date>` reply in that thread approves them all (`.sdlc/scripts/descopes-decided.sh` reads it). A line in build.md or the PR body is never the approval: any session can write one. An amendment that build.md doesn't record, or that `## Plan changes` doesn't list, gets its own Important thread instead. An amended spec clause still gets clause coverage (pass 3). With the variable off or unset, a code PR that changes `plan.md` or `spec.md` fails the `pr-title` check: say in the summary that the change goes through a plan or spec PR. <!-- rule: review.plan-amendments -->
   - **Decisions made in the build session share one thread (#218):** a descope that build.md's Deviations records as decided by a person in the session (who, when, their words), and that the PR body lists under `## Descopes decided in session`, gets no thread of its own. Post **one** thread for all of them and any plan amendments, starting `**Important (product owner decides; engineer for plan amendments):** Session decisions: needs approval.`, listing each with its requirement, what was delivered and build.md's record. One `Approved: <name>, <date>` reply from a person approves them all; any other reply sends them all back. An unrecorded or unlisted descope keeps its own Descope thread. <!-- rule: review.session-decisions -->
6. **Project rules:** if the repo has `docs/review-rules.md`, apply each rule it lists to the diff. That file is the project's own: the sync never touches it, so a project adds its rules there, never by editing this file. Report a broken rule at the severity the file gives it, or as Important if it gives none, and say who decides as it says (the engineer, unless it names someone else). With no such file, skip this pass. <!-- rule: review.project-rules -->

## Severity

- **Important:** wrong behaviour, a security issue, or a spec requirement that isn't met. Always report these. <!-- rule: review.severity-important -->
- **Nit:** style or naming. Report at most 3 per PR, and none if any Important finding exists. <!-- rule: review.nit-cap -->

## Exclusions

- Anything `make lint` or `make test` already enforces. CI reports those failures. <!-- rule: review.exclusions -->
- Lockfiles and generated files.
- Wording in `intent.md` and `spec.md`: how it is phrased is for the product owner. Whether every clause of a requirement is covered (passes 3 and 4) is not wording, and is in scope.

## Writing findings

The product owner and code owners read findings on GitHub, often without the files open. Make every finding readable on its own: <!-- rule: review.finding-readable -->

- **Quote what you refer to.** Never cite a bare ID like "A8" or "R2". Quote the line: `> A8. The existing change … prints \`…\tspec\t0\``.
- **Say why it matters** in one sentence: what goes wrong, and when.
- **Suggest a fix**, as replacement wording or code where you can.
- **Say who decides:** *product owner* for intent and spec content, *engineer* for plan and code.

## Posting findings

A finding the summary mentions but no thread holds blocks nothing: conversation resolution only sees threads (spellbound3d#124 merged with three Important findings in its summary and no threads, #130).

- **Every Important finding is its own review thread,** and its first line starts with `**Important`: `**Important:**`, or `**Important (product owner decides):**` to name who decides. Put it on the line it's about with the inline comment tool. When no line in the diff fits (a finding about the whole PR, such as a missing change folder or spec, or a binary file), comment on the most relevant file in the diff instead, with exactly this command: `gh api repos/<repo>/pulls/<N>/comments -f subject_type=file -f path=<file> -f commit_id=<head sha> -f body=<finding>`. Never leave an Important finding only in the summary. <!-- rule: review.important-thread -->
- **A descope's thread says so:** every Important finding about something left undone, untested or unchecked that nobody approved (pass 5, delivery gaps included) has `Descope: needs approval` right after its lead-in: `**Important (product owner decides):** Descope: needs approval. …`, or `(engineer decides)` for a plan or code descope. The `claude-review` status stays failed until a person (not a bot or an App) replies in the thread, whether or not it's resolved (#132, `.sdlc/scripts/descopes-decided.sh`). A reply with `Approved: <name>, <date>` approves the descope; any other reply sends it back to be built, and then the next review checks it was: post a new thread if it wasn't. The summary names who approved each one. <!-- rule: review.descope-thread -->
- **A Nit may get a thread too,** starting with `**Nit:**`. Nits are never counted. <!-- rule: review.nit-thread -->
- **On a re-review,** an earlier Important thread that is still unresolved still counts: don't post it again. Whether a thread is resolved comes from `.review-threads.json`, which the workflow writes before the review (#220), never from a guess. A finding whose thread was resolved but which still isn't addressed gets a new thread. <!-- rule: review.rereview-open-threads -->
- **The summary's last line** is a hidden count: `<!-- review-findings: important=<N> nit=<M> -->`, where N is the number of unresolved Important threads once this review is posted (new ones and earlier ones still open). The `claude-review` status fails when the line is missing, or when N isn't the number of unresolved `**Important` threads the reviewer started (`.sdlc/scripts/review-findings.sh`). That's the gate: an approval given before the review posts is safe only because of it. <!-- rule: review.hidden-count -->

## Summary comment

Keep exactly **one** summary comment per PR, and replace it on each new review rather than adding another. It contains: <!-- rule: review.one-summary -->

1. Each **Descope: needs approval** finding, then the descopes, each quoted with who approved it or "not approved", the human checks still to try, and the plan's Risks that need a decision. These come first.
2. The number of findings per severity, and whether each earlier finding is now resolved.
3. On a re-review, **every earlier note** (#242): `.review-earlier-summary.md` holds the summary you're replacing and the PR's commits. Carry over each note there that asked for something outside a thread (a stale PR body, a missing approval), one line each: `✅ <note> — addressed in <short sha>` (or `PR body updated`, `approved by <name>`), or `⬜ <note> — still open`. Check before ticking, and never drop one. A note now held by a thread links to it. <!-- rule: review.earlier-notes -->
4. One line per open finding: a short quote of the text it's about, the owner who decides, and a link to its thread.
5. One line on whether the change matches its spec, saying what was compared, and claiming only what was checked. For example: "Every clause of R1–R45 traced to an acceptance criterion and to a plan step and test (112 clauses)", or "IDs only: every acceptance criterion has a Verification row". <!-- rule: review.claim-only-checked -->
6. How to handle the findings, as a one-line reminder:
   - Whoever decides runs `/sdlc-pr <N>` in Claude Code: the product owner for `intent:`, `bug:` and `spec:` PRs, the engineer for the rest.
   - Tagging `@claude` on a thread is optional. It hands that finding to the GitHub bot instead, so don't do both for one finding.
7. Last, the hidden count line from [Posting findings](#posting-findings).
