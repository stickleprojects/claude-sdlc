# Settings

The pipeline's defaults suit a small team. A project changes them in one of three places, depending on what reads the setting:

- **A line in the repo's `CLAUDE.md`:** the skills read these, so they change how Claude works in a session. Add the line anywhere in the file.
- **A repository variable** (`gh variable set <NAME> --body <value>`): the workflows read these, so they change what CI does.
- **An environment variable** in the session: the hooks read these.

A setting that isn't there takes its default.

## In CLAUDE.md

| Line | Values | Default | What it changes |
|---|---|---|---|
| `Bug path:` | `fast`, `full` | `fast` | `fast`: `/sdlc-intent` puts a small bug with a known cause into one PR, holding its report, short spec, failing tests and fix, so approving it ships the fix (#148, #160). A bug that needs a product decision, a design decision, a new dependency or a data migration still takes the full path ([bug-fast-path.md](bug-fast-path.md) says what it skips and what it can't). `full`: every bug goes through a bug PR, a spec PR, a plan and a build, and CI's `pr-title` check fails a bug fix with no plan. CI reads the line from `main`'s CLAUDE.md. |
| `Tooling paths:` | path prefixes, space-separated (`scripts/ tools/ .github/`); an entry ending in `/` is a folder, any other a file or folder | none: the tooling path is off | Turns on the tooling path (#221): a change whose `intent.md` has the line `Kind: tooling` goes through one PR holding its intent, plan and code, with no spec, titled `chore(<slug>)` or `ci(<slug>)`. CI's `pr-title` check fails such a PR if its code touches anything outside these paths, or if the line isn't there. CI reads the line from `main`'s CLAUDE.md, so a PR can't widen it for itself. [tooling-path.md](tooling-path.md) says what it skips and what it can't. |
| `Local check:` | make target names, space-separated (`preflight`, or `check coverage`); `make` and backticks are allowed | `check`, then `coverage` if the Makefile has it | What `make local-check` runs: the local check before a push or a PR that the build skill, the build template, the verifier and the review-findings and identity skills run (#253). Coverage runs locally only if the line names it; otherwise the PR's CI runs it, and local-check's last line says `coverage: in CI`, which build.md's status and the PR body repeat. So a green local check then means only what the line names passed, not the full suite or coverage: pair it with `SDLC_PR_CHECK_TARGET` and main's `make check FULL=1`, and main can go red after a merge. A name that isn't a target in the Makefile fails `make validate`, naming the line (`.sdlc/scripts/local-check.sh`). |
| `Change tracking:` | `issues` | change folders | `issues`: changes are tracked as GitHub issues, not `changes/` folders, and the review stops asking for a change folder. The framework repo uses it. |

## Repository variables

| Variable | Values | Default | What it changes |
|---|---|---|---|
| `SDLC_AUTO_MERGE` | `merge`, `squash`, `rebase`, `off` | off | Turns on GitHub's auto-merge for the PRs the pipeline opens, and re-reviews each push (team mode only; see the readme). |
| `SDLC_CHECK_AFTER_REVIEW` | `on`, `off` | off | `on`: a PR's `check` (`make check`) waits for a clean Claude review, one with no open Important thread, and runs only then (`sdlc-check-after-review.yml`). A review that asks for changes never costs a `check` run, which helps on a runner that runs one job at a time. A PR then takes longer to pass both, since they run one after the other. Pushes to main and fork PRs run `check` straight away. Use it with `SDLC_AUTO_MERGE`, which reviews every push; without it, a push waits for the `review` label before `check` runs. The `check` label runs `make check` now, whatever the review says. In the PR's checks, CI's job shows as `check: waits for the Claude review` and finishes in seconds on `SDLC_RUNNER` without running anything (#236); the `check` that counts is the commit status. It always holds the newest real `make check` on the head, pass or fail, and links to its run: the PR's list shows skipped or cancelled copies of `make check (after review)`, never the copy that ran, because that one runs from main (`workflow_run`, #219). Once a gate lets `make check` through, `check` reads `make check is queued` until the job starts, and other gates on that head leave it alone (#237); if it never starts, the `check` label runs it. |
| `SDLC_PR_CHECK_TARGET` | a make target name | `check` | The make target a PR's `check` runs, for a project whose `make check` is too slow to run on every push (#244). Set it to a lighter tier you add beside `check`, such as `check-pr`: lint, validate and the fast tests. Pushes to main still run `make check FULL=1`, and `make check` stays the full check everywhere else, including the local check unless CLAUDE.md's `Local check:` line names another. So a green `check` on a PR then means the PR tier passed, not the full suite, and main can go red after a merge; run the full check on a schedule, and gate releases on it. A name that isn't a target in the Makefile fails `check` with a message naming the variable (`.sdlc/scripts/pr-check-target.sh`). It applies with or without `SDLC_CHECK_AFTER_REVIEW`. |
| `SDLC_MAIN_DOCS_SKIP` | `on`, `off` | off | `on`: a push to main that changed only docs runs `make validate` instead of `make check FULL=1` (#240), which saves a full run for every intent, spec, plan or docs merge. Docs are `docs/**`, `changes/**` and top-level `*.md`, the same split the plan check uses (`.sdlc/scripts/main-docs-only.sh`, from the push's `before` to its `after`). Any other file, a diff it can't read, or no earlier commit runs the full check, so main's full run still catches what a PR's lighter check missed. `off`: every push to main runs `make check FULL=1`. Either way the `check` job is green, so anything that needs a fully checked commit (a release gate, a scheduled run that skips commits already checked) reads which step ran from the jobs API: `make check FULL=1 (push to main)` succeeded for a full run, and `make validate (docs-only push to main)` for a docs-only one; the other is `skipped`. Those step names don't change. |
| `SDLC_BUILD_AMENDS_PLAN` | `on`, `off` | off | `on`: a build PR may amend its own change's `plan.md`, and `spec.md` where a decision changes a clause, when its body lists each amendment under `## Plan changes` and build.md records who decided (#174). The review raises them all in its one "Session decisions: needs approval" thread, beside any descopes decided in the session (#218), and a person's single `Approved: <name>, <date>` reply approves them, which `claude-review` waits for, as for a descope. The PR keeps its `feat` or `fix` title (`pr-title`). `off`: mid-build plan changes go through a plan or spec PR. |
| `SDLC_REVIEW_CARRY_FORWARD` | `on`, `off` | on | Without auto-merge, a push that only merges the base branch in (GitHub's **Update branch**) keeps the PR's review when git's own merge gives exactly that commit, and the base's changes it brings in touch none of the files the PR changes (#182). Otherwise `claude-review` says "Not reviewed" and the `review` label runs a fresh one. `off`: every push needs a fresh review, base merges included. |
| `SDLC_REVIEW_EXTRA_BOTS` | bot names, comma-separated | none | Bots whose PRs the Claude review accepts, such as `renovate` (see the readme). |
| `SDLC_RUNNER` | a runner label | `ubuntu-latest` | Runs every framework job on your own runner (`self-hosted-runner.md`). |
| `SDLC_RUNNER_HEAVY` | a runner label | `SDLC_RUNNER` | Runs the jobs that run `make check` or the evals (CI's `check`, `make check (after review)` (the post-review `make check`), the agent evals) on a bigger runner, while the rest stay on `SDLC_RUNNER` (#222, `self-hosted-runner.md`). |
| `SDLC_AGENT_APP_ID`, `SDLC_AGENT_APP_SLUG` | the App's id and slug | none | The GitHub App Claude acts as (`setup-agent-apps.md`). |

## Environment variables

| Variable | Values | Default | What it changes |
|---|---|---|---|
| `SDLC_PLAN_GATE` | `0` | on | `0` turns off the hook that blocks code before `plan.md` is committed. CI still checks it. |
| `SDLC_LOCK_TESTS` | `1` | off | `1` locks every test file, not only a bug fix's failing test. |
